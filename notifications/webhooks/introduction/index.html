    Webhooks

    Webhooks let your systems react to your orders in real time. Instead of repeatedly polling our API to check whether something has changed, you register a URL and we send an HTTP POST request to it the moment an event happens, for example when an order is validated or a new delivery is published.

    Typical uses:

    • Alert your own customers as soon as a new delivery is available.
    • Automatically download new data via the STAC API.
    • Keep order statuses in your own systems in sync with ours.

    How it works

    1. You register a webhook endpoint: an HTTPS URL on your server and the event types you want to receive.
    2. We give you a signing secret for that endpoint.
    3. When a subscribed event happens on an order in your workspace, we send a JSON POST request to your URL.
    4. Your server verifies the signature and responds with a 2xx status code.
    5. If your server doesn't respond with a 2xx, we retry on a fixed schedule.

    Webhooks are workspace-scoped

    An endpoint receives events for all eligible orders in its workspace, regardless of who placed them. Webhook notifications are currently only sent for standing LST Precision orders; other products aren't yet supported. Deleted orders don't trigger webhooks. Webhooks are independent of email notifications.

    Quickstart

    1. Create an endpoint on your server

    Your endpoint must:

    • Be reachable from the public internet over HTTPS.
    • Accept POST requests with a JSON body.
    • Respond with a 2xx status code *.

    For a complete example that also verifies the signature, see verify_webhook.py.

    Testing locally

    To receive webhooks on your own machine during development, expose your local server through an HTTPS tunnel (for example ngrok) and register the tunnel's URL.

    2. Register the endpoint

    1. Go to Account > Workspace > Webhooks.
    2. Click Create Webhook and enter your endpoint URL, the events to subscribe to and, optionally, a description.
    3. Copy the signing secret shown after creation.

    From the same page you can edit or delete an endpoint, rotate its signing secret, and view its delivery history in the Events log. See the UI documentation for a step-by-step guide with screenshots.

    curl -X POST https://api.constellr.com/webhook-endpoints \
  -H "X-Api-Key: $CONSTELLR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"url": "https://example.com/webhooks/constellr", "event_types": ["delivery.published"], "description": "Production order events"}'

    See Swagger or ReDoc for the full request/response schema.

    The signing secret is shown only once

    The secret is returned only when the endpoint is created (and when it is rotated). Store it securely right away; it can't be retrieved later.

    3. Verify incoming requests

    Use the signing secret to check that each request really comes from constellr and hasn't been tampered with. See Verifying webhooks.

    4. Receive your first event

    Placing an order does not by itself trigger a webhook. Events are sent as an existing order progresses: wait for it to be validated, rejected or closed, or for a new delivery to be published, and check the request arriving at your endpoint. You can review every delivery attempt, including your server's response, in the endpoint's delivery history through the UI or the API.

    Managing endpoints

    Endpoints and their delivery history can be created and managed through the UI or the API.

    Best practices

    • Respond quickly. Return a 2xx as soon as you've received and verified the request, and do any heavy processing (e.g. downloading data) asynchronously. Requests time out after 20 seconds.
    • Always verify signatures before trusting the payload. See Verifying webhooks.
    • Handle duplicates. Delivery is at least once, so the same event may arrive more than once. Use the webhook-id header (equal to the event id) to ignore events you've already processed.
    • Don't rely on ordering. Events may arrive in a different order than they happened. Use the event timestamp if order matters.
    • Subscribe only to what you need. Each endpoint only receives the event types it's subscribed to.
